# ServerGuard 深度分析报告

> 分析日期：2026-08-17
> 分析框架：**有用 → 能用 → 好用 → 零风险 → 自动化** 五轴评估
> 本轮同时完成了 8 项关键缺口修复（见第三节），全部有 git 提交与测试背书。

---

## 一、五轴评估结论

### 1. 有用 ✅ —— 痛点真实，定位精准

产品瞄准"没有专职运维的中小团队/个人站长"，解决的四个痛点都有真实市场：

| 用户痛点 | 现有方案的问题 | ServerGuard 的答案 |
|---|---|---|
| 凌晨故障无人值守（磁盘满/OOM/服务挂） | Zabbix/Prometheus 只告警不处置，"告诉你服务器死了" | 自动清理/重启/封禁，"不让它死" |
| 监控栈太重 | Zabbix 吃 600MB 内存，需要数据库+组件 | 单二进制 ~16MB，SQLite 零依赖，内存限 80MB |
| 告警疲劳 | 半夜被 P2 告警吵醒 | 抖动抑制+同源合并+分级路由+凌晨 P2/P3 延迟到早 8 点 |
| SSL 证书过期 | 手动续期易忘 | 提前 14 天错峰续期 + LE→ZeroSSL→TrustAsia 三 CA 降级 |

差异化定位（对标宝塔"不管自愈"、monit/supervisor"只管进程"）清晰，26 个守护模块覆盖面完整。**这一轴不需要加功能，需要的是把承诺变成可验证的现实。**

### 2. 能用 ⚠️→✅ —— 本轮修复了四个"链路断裂"

分析时发现的断裂点及修复状态：

| 断裂点 | 影响 | 状态 |
|---|---|---|
| Hub 远程命令是占位符（收到 restart 只打日志） | 多机管控控制不了任何东西 | ✅ 已落地 4 个白名单命令（见 3.1） |
| Docker 部署引用不存在的配置文件 | `docker compose up` 必挂 | ✅ 已修复（见 3.2） |
| sgctl 四组子命令后端与参数不对齐 | import/export/db/security-check 半残 | ✅ 已补全（见 3.3） |
| 端到端零验证 | "装上→5 分钟出效果"无背书 | ⚠️ 部分：单测 23 包全绿+三平台交叉编译通过；真实 Linux 环境部署验证仍缺（见路线图） |

### 3. 好用 ⚠️ —— 骨架好，首跑体验待实测

- 24 个面板视图 + 文档齐全（README 614 行、安装/运维/API/CLI 手册）
- 学习模式默认开启（首周只告警不动作），符合"零风险上手"
- 本轮改进：`sgctl doctor` 新增数据目录可写探针 + Hub 连接状态检查；`/api/status` 暴露 Hub 连接态
- 待办：真实服务器上验证"安装→5 分钟看到守护效果"的完整旅程；面板首屏引导

### 4. 零风险 ⚠️ —— 机制设计优秀，验证欠账（本轮已补关键背书）

五层安全机制比自评文档（2026-08-09）更新，此前认为缺失的部分实际已落地：
`ban_unban_breaker`（封禁振荡熔断）、`post_kill_evaluator`（Kill 后 5 分钟对比，更差则自动紧急停止）、`emergency_rollback`（SSH 失联回滚）、`cpu_trigger_tracker`（连续 3 次才 Kill）、依赖链状态机均有实现**且大多有测试**。

本轮补上：
- 紧急停止契约测试：触发后阻断一切 Kill、恢复后放行、halt 模式连采集都停
- Hub 命令安全契约测试：白名单之外无可执行路径、command_id 正确回传、result 载荷完整
- **安装脚本随机面板密码**：原为固定 admin123 且打印在横幅（安全产品的致命伤），现安装时生成随机密码

仍存在的风险项（建议尽快处理）：
1. **`tmp/reseed.go` 等遗留脚本硬编码了生产环境管理员明文密码**（sg.jjtt.net 后台），建议立即删除文件并修改该密码
2. `go test ./...` 会被 `tmp/` 下多个 package main 脚本卡住（本轮以 `./internal/... ./cmd/...` 范围运行）
3. 审计/回滚机制有，但**从未做过真实故障演练**（拔网线/杀进程/写满磁盘），建议按 tests/chaos 用例在测试机执行一轮

### 5. 自动化 ✅ —— 理念正确：自动处置必须包裹在安全机制里

学习模式默认（首周只告警）→ 低风险动作自动（僵尸清理/日志压缩/证书续期）→ 高风险动作需确认（白名单进程重启/宝塔服务重启）→ 一键导入存量守护配置（monit/supervisor/systemd/pm2/宝塔，按名称去重可重复执行）。

本轮增强：Hub 远程 pause/resume 让"人在外地也能一键停止自动修复"；db cleanup 按差异化保留策略自动执行（审计 WORM 不动）。

## 三、本轮完成的修复（全部已提交，共 7 个 commit）

### 3.1 Hub 远程命令从占位符变为真实实现
- **Agent 端**（`cmd/serverguard-agent/main.go`）：注册 4 个白名单命令处理器——`restart`（优雅退出，由 systemd/服务管理器拉起）、`status`（健康评分/安全模式/磁盘水位快照）、`guard.pause`/`guard.resume`（远程紧急停止与恢复，全程发告警留痕）
- **协议**（`internal/comm/hubclient.go`）：处理器可返回结果数据，`command_response` 携带 result；修正 command_id 提取错误（原来把整个 data 当 command_id 回传）
- **Hub 端**（`internal/hub/api/`）：白名单扩展至 4 命令；新增 `POST /api/servers/:id/command` 通用下发 API（双端白名单校验，杜绝任意命令执行）；命令响应审计记录命令名与成败

### 3.2 Docker 部署修复
- Dockerfile CMD 改指真实存在的 `configs/serverguard-agent.yaml`
- docker-compose：挂载真实配置、数据卷对齐 `storage.path`、端口对齐 `web.listen`、`pid: host` 支持宿主机进程监控、移除未接线的 postgres（Hub 默认 SQLite）
- 新增 `configs/hub.yaml`（Hub 最小可用配置，标注 jwt_secret 兼作 Agent 接入 Token）

### 3.3 sgctl 运维链路补全

### 3.4 安全与测试

## 六、V4.0 智能化升级（第二阶段：更智能、更好用）

在第一轮"能用/零风险"修复之后，第二阶段围绕"会推理、会积累经验、更好上手"完成升级：

### 6.1 更智能 —— 四项能力

**① 根因链推理引擎**（`internal/agent/correlation/`）
- 5 分钟窗口内，按 6 条领域因果规则（数据库故障→服务超时、内存不足→进程被杀、磁盘满→写入失败、CPU 饱和→响应劣化、网络故障→外部不可达、证书问题→访问异常）+ 同源连锁，把多条告警用并查集聚类成一条故障事件（Incident）
- 输出一条"说人话"的汇总告警：根因（时间）→ ↓引发 → ↓引发，附自动处置清单与历史经验，替代 N 条孤立告警
- 零风险设计：旁路后处理（不拦截不延迟原始告警）、确定性规则可解释、链长≥2 才成事件
- 规则自我验证：参与多次事件却从未伴随真实处置的规则自动停用观察（防误报积累）
- **测试 11 例**覆盖聚链/防误聚/防倒果为因/防自循环/指纹归并/动作挂载/知识沉淀

**② 知识库反哺闭环**（`internal/agent/knowledge/`）
- 事件解决后聚合沉淀（同症状指纹累加计数、保留历史有效处置）
- 下次同类故障，汇总告警直接带出："该症状已出现过 N 次，上次处置 X（success）"——第 3 次出现时建议"彻底排查根因而非反复重启"
- 服务器越用越聪明，是竞品给不了的体验差异

**③ 预测性自愈**（`internal/agent/forecast/enhanced_predictor.go`）
- 内存泄漏预测：进程 RSS 线性回归（复用磁盘预测模型），≥0.5MB/h 判增长，48h 剩余预警 / 12h 紧急，附维护窗口重启建议；已接线进主循环 5 分钟采样
- 证书续期风险：ACME 失败队列 × 域名到期关联（3 次失败+≤7 天=高风险，建议多 CA 降级）
- **测试 9 例**覆盖检出/防误报/分级/清理/风险排序

**④ LLM 增强层（默认关闭）**（`internal/hub/api/v40_api.go` + `ai` 配置段）
- `ai.enabled` 零值默认 false，不配置密钥则完全不走外部 API——低依赖原则
- 可选开启：告警人话化、周报润色、事件解释（`/api/llm/explain-incident/:id`）

### 6.2 更好用 —— 四项能力

**⑤ 首跑引导向导**（Onboarding.vue + `/api/onboarding/*`）：检测宝塔/Nginx/MySQL 等存量服务 → 一键导入守护 → 学习模式倒计时，把"装上"变成"5 分钟看到它在干活"

**⑥ 通知双向交互**（`internal/notifier/bidirectional.go` + `POST /api/notify/reply`）：告警带动作码，回复 1=确认 / pause=暂停自动修复 / resume=恢复——人在手机上完成闭环，pause 动作已接线 SafetyManager 紧急停止

**⑦ 场景模板**（`internal/guards/config/scene_template.go`）：wordpress / nginx-mysql-redis / spring-boot 三个内置模板，一键应用写入规则（合并模式不覆盖已有）+ 守护目标

**⑧ 告警落地页闭环**（AlertLanding.vue + `/api/incident-by-alert/:alertId`）：点开一条告警即见根因链、自动处置记录、建议动作

### 6.3 第二阶段验证

- 新增测试 23 例（correlation 11 + forecast 9 + scene_template 3）
- 全量 `go test ./internal/... ./cmd/...` 通过（详见 git 提交记录）
- 全部智能能力均为旁路/可选设计，不增加主监控链路风险
